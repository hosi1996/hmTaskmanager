## نقش‌ها
- **سیستمی:** OWNER (همه‌چیز) / STAFF / CLIENT
- **پروژه:** VIEWER < REPORTER < CONTRIBUTOR < MANAGER
- Viewer/Reporter (و هر مشتری غیر مدیر) فقط تسک‌هایی را می‌بینند که سازنده/اساین/دنبال‌کننده‌شان هستند. Contributor کارمند و Manager همه‌ی تسک‌های پروژه را می‌بینند.

## مسیر توسعه‌ی بعدی
Webhook خروجی/API عمومی (توکن API در جدول جدید + همان `access.js`)، PWA، اعلان ایمیلی (SMTP)، جستجوی کامل‌تر با `pg_trgm`/tsvector.

## ماژول مانیتورینگ دامنه
پروژه‌ی جدای `uptimebot` (پایتون + python-telegram-bot) به‌جای اینکه به‌صورت سرویس مجزا کنار سیستم اجرا شود، به‌عنوان یک ماژول داخل خودِ بک‌اند (`modules/monitoring`) بازنویسی شد:
- **چک‌ها** عیناً پیاده‌سازی شدند (DNS/NS/MX با `node:dns`، Ping با اجرای باینری سیستم، SSL با `node:tls`، HTTP/HTTPS/ریدایرکت/سرعت با `fetch`، انقضای دامنه با RDAP)؛ `iputils` به Dockerfile بک‌اند اضافه شد تا `ping` در دسترس باشد.
- هر دامنه به یک **پروژه** وصل است، نه یک چت تلگرام مستقل؛ گزارش مشکل به همان گروه تلگرامی می‌رود که پروژه به آن وصل است (از زیرساخت موجود `lib/notify.js`/`tgSend` استفاده شد) و هم‌زمان یک نوتیفیکیشن داخل پنل برای مدیران پروژه ساخته می‌شود.
- زمان‌بندی با یک تیک هر ۲۰ ثانیه (`modules/monitoring/scheduler.js`) و قفل Redis مشابه `scheduler.js` موجود انجام می‌شود؛ هر دامنه بازه‌ی زمانی مستقل خودش را دارد.
- «محل چک» (خارج/ایران/هر دو) دقیقاً مثل ربات اصلی، از طریق همان `iran-checker/check.php` (بدون تغییر، فقط کپی‌شده) با یک URL/Token قابل‌تنظیم در پنل مدیریت انجام می‌شود؛ اگر تنظیم نشود، آن گزینه غیرفعال می‌ماند.
- دسترسی مدیریت دامنه‌ها فقط برای MANAGER/OWNER پروژه است (نه مشتری)، چون داده‌ی فنی داخلی است، نه چیزی که مشتری باید ببیند.
